## Answers (2026-10-21)

Tested through the Google Drive connector attached to Claude Code; API facts from Google's docs (Sources).

1. **Markdown coverage.** Writing: uploading `text/markdown` converts to a native Doc and keeps H1-H6, bold, italic,
   inline code, links, nested bullet and numbered lists (a list starting at 5 keeps its start), tables with bold
   cells, blockquotes (as an indented paragraph), horizontal rules, checkboxes, and footnotes (real Docs footnotes).
   Fenced code blocks are lost: the lines become plain Arial body paragraphs with blank lines between them, and
   indented code loses its indent. Reading: `text/markdown` export returns the content with these changes: every
   heading comes back wrapped in `**`, `-` inside text is escaped as `\-`, soft line breaks are joined into one
   line, `_italic_` becomes `*italic*`, 4-space nesting becomes 2-space, list items gain two trailing spaces, the
   final newline is dropped. A second round trip is stable except the code indent.
2. **HTML blocks.** Raw `<div style="color:red">` inside markdown survives as red text, so inline styles do apply.
   `<details>` is destructive: its text merged into the next heading. A whole-document `text/html` upload keeps
   headings, bold, italic, links, tables, strikethrough, underline, inline color and background, and images, but
   nested `<ul>` loses its nesting, `<pre><code>` becomes per-line inline monospace rather than a block,
   `<blockquote>` becomes a plain paragraph, and `<sup>` is lost on export. No API inserts HTML into an existing
   Doc; HTML only enters through conversion on upload. The native "Code blocks" building block is UI only, paid
   Workspace editions only, and no Docs API request creates one.
3. **Two-way sync.** Possible only as semantic sync, never byte sync. Every pull reformats the markdown (item 1): on
   a 45-line resume-style sample with zero content change, the round trip changed about 30 lines. A sync would need
   a normalizer (strip heading bold, unescape `\-`, re-nest to 4 spaces, drop trailing spaces, restore soft breaks)
   and conflict detection on normalized text, and an edit made in Docs has no guaranteed mapping to one markdown
   line. This is the familiar fight with a formatter that rewrites untouched lines. Through this session's connector
   a push is create-a-new-file: Drive `update_file` is metadata only, so the link changes each push unless the Docs
   connector is attached (it is not, here) or a script calls `files.update` with `text/markdown` directly. One-way
   push with Docs as a read-only copy is cheap and reliable; a resume-style document uses only features that survive
   (fixture 03: headings, nested lists, rules, bold labels; no code blocks, tables, HTML, links, or footnotes).
4. **Named versions.** No. The Drive v3 Revision resource has no name field, the Docs API and Apps Script have no
   version methods, and `keepForever` applies only to binary files. `revisions.list` works for Docs (Google warns
   it may be incomplete). This connector's download accepts a `revisionId` but exposes no way to list revisions.
   Substitutes: a `files.copy` snapshot titled with the version, or the `Version:` line already in the document.
5. **Paths.** See Options and Comparison of the top 3.

## Recommendation

Try first: **C, own script, one-way push** from the repo to one native Doc.

- why: the only path that keeps one link, runs from a git hook or cron with no LLM in the loop, and is deterministic;
  a resume-style document uses only features the converter keeps, so the Doc matches the repo after every push.
- why not: one-time OAuth setup and a refresh token to keep safe; the in-place markdown update is documented but
  untested, so step one is proving it on a scratch Doc; adding fenced code to a synced file later would silently
  degrade in the Doc.
- side effects: every push overwrites the Doc, so edits made in Docs are lost unless pulled and merged first; version
  history gains one unnamed revision per push.

Try second, only if interactive AI editing of other Docs matters: **B, the Google Docs connector** on claude.ai.

- why: the only path where Claude edits an existing Doc in place and can propose suggestions instead of overwriting.
- why not: non-deterministic; the skill reference lists many failure modes (stale indexes, headings losing bold,
  typed list markers); not usable from Claude Code; eligibility by plan is not published.
- side effects: enabling it grants Claude write access to every Doc in the account; a wrong batch lands in the real
  file, mitigated only by the revision guard and version history.

Not recommended on its own: **A**. Create-only, so each push makes a new link. Keep it as the zero-setup read path
and for one-off creates.

### Per-tool notes

Paths are inside each repository. Nothing was executed; the clones were read as data.

**gdoc-sync** (MattHandzel, Python >= 3.10, v0.9.0, created 2026-07, CI on Linux and macOS)

- Write pipeline is markdown to pandoc docx to `files.update` on the same id; multi-tab docs instead compile the
  pandoc AST into Docs API requests (`src/gdoc_sync/push.py`, `mdrequests.py`, `tabs.py`). Needs pandoc installed.
- Reads with `documents.get(includeTabsContent=True)` and its own renderer `doc_to_markdown`
  (`src/gdoc_sync/convert.py:137-266`): headings, bullets, code detected by monospace font, tables, footnotes.
  Blockquotes do not round-trip. Suggestions are rendered as if accepted.
- Change detection keeps two snapshots per file, `base_local` and `base_remote`, and compares each side only to
  its own snapshot. `revisionId` is explicitly rejected because Google churns it; a sha256 text fingerprint guards
  the render-to-upload race (`convert.py:596-640`, `push.py:95-102`).
- Merge is `git merge-file --diff3` with a pure-Python diff3 fallback (`src/gdoc_sync/merge.py`, about 300 lines,
  no Google dependency). Conflicts leave git-style markers or a `.remote.md` sidecar and set a sticky conflict state
  until `resolve`. Backups kept (20). Refuses to push if the file shrank below 20% or the Doc rendered below 50% of
  the baseline, a cheap guard against pushing an empty file.
- Comments round-trip as CriticMarkup `{>>Author: text<<}`; replies and resolves push through the Drive comments
  API. New anchored comments are impossible (a Google bug is cited).
- Checkboxes: nothing in the source; pandoc would emit U+2610/U+2612 glyphs, so `- [ ]` would arrive as text.
- 18 subcommands including `watch`, `doctor`, `share`, `restore`; `--dry-run` only on one novelty command.
  State in `~/.local/state/gdoc-sync/state.yaml` plus `bases/` and `backups/`; config in `~/.config/gdoc-sync/`.

**md-gdoc** (MattFisher, Python >= 3.10, v0.2.0, two contributors, one of them "claude")

- Writes through the Docs API only, on purpose: `documents.create` then `batchUpdate` with insertText,
  updateParagraphStyle, updateTextStyle, createParagraphBullets, insertTable (`src/md_gdoc/requests_builder.py`).
  Incremental pushes diff local blocks with `difflib.SequenceMatcher` and replace only changed ranges, which keeps
  comment anchors on untouched blocks; `--replace` clears the body. Alignment requires the Doc's block count to
  equal the snapshot's, so any structural edit made in the UI forces `--replace`.
- Reads with `files.export(text/markdown)` then `clean()` (`src/md_gdoc/unescape.py`): CRLF to LF, strips the
  backslash escapes Google adds to `` \ ` * _ { } [ ] ( ) # + - . ! | < > ~ " ' ``, collapses blank runs, turns
  code-font paragraphs back into fences; then `mdformat` with the gfm plugin normalizes bullets, trailing spaces,
  and `:----` separators. The e2e golden file documents what Google emits (`tests/e2e/fixtures/`).
- Two snapshots in `.sync/` next to the file; pull overwrites local when only the Doc changed, otherwise writes
  `<file>.remote.md` and leaves the merge to a human. Push refuses on divergence unless `--force`. No three-way
  merge by design (`docs/superpowers/specs/2026-07-02-gdoc-sync-design.md`).
- Request ordering lesson worth keeping: insert a whole list as one insertText with tab prefixes, apply paragraph
  styles, then text styles, then createParagraphBullets last because it consumes the tabs
  (`requests_builder.py:175-211`). `batch_update` has 429 backoff (`api.py:109-120`).
- Comments are read-only into `<file>.comments.md`; push warns when a changed block holds a comment's quoted text.
  Images are dropped on push and extracted to `<name>.assets/` on pull. Footnotes only with `--replace`.
- Checkboxes: `- [ ]` is pushed as a bullet whose text is the literal `[ ]`; native Docs checklists are not handled.
- Doc id and url live in the markdown file's YAML frontmatter (`gdoc_id`, `gdoc_url`, `tab_id`).

**gdoc** (LucaDeLeo, Python >= 3.10, v0.23.0, 20 stars, 5 contributors, about 1,850 tests, CLI plus MCP server)

- Whole-document write is exactly our planned call: `files.update` with media mimetype `text/markdown`, body
  mimeType `application/vnd.google-apps.document`, `fields="version"`, same file id so the link survives
  (`gdoc/api/drive.py:176-200`). `new --file` uses `files.create` with `text/markdown`. Partial edits, inserts,
  suggestions, and tables go through `batchUpdate` with a custom markdown-to-requests parser (`gdoc/mdparse.py`).
- Reads with `files.export(text/markdown)` raw; no normalization on the pull path. A de-escape loop
  `re.sub(r"\\([^\w\s])", r"\1", s)` exists only for diff display (`gdoc/revdiff.py:171-188`).
- Change signal is the Drive `version` integer stamped into frontmatter as `gdoc-version: N`; `version` is read
  before the export so the stamp can only be older than the content, never newer. Push refuses (exit 3) when the
  Doc's version moved past the stamp unless the current export already equals the local body; `--force` is
  last-writer-wins. The code acknowledges false conflicts from cosmetic Docs edits (`cli.py:2102`). No snapshot,
  no merge; recovery is pull to a new path and `gdoc diff`.
- Ships Claude Code PreToolUse/PostToolUse hooks that auto-pull before an agent reads a stamped `.md` and auto-push
  after it writes (`cli.py:2446-2800`). This is the closest existing thing to "AI edits the markdown, human edits
  the Doc".
- Full Drive comments API (list, add, reply, resolve, reopen, delete), anchored comments only when the Cloud
  project is in Google's Workspace preview program, suggestions via `suggest`.
- Checkboxes: none; `gdoc/listnest.py` refuses checkbox-glyph lists outright.
- Surprises: `gdoc --help` updates itself over the network; README claims MIT but no LICENSE file is in the tree;
  `cli.py` is 5,600 lines, so pieces are copied, not imported.

### What the review changes in the plan

- In-place update is proven in the wild: gdoc ships `files.update` with a `text/markdown` body on the same Doc id
  (`gdoc/api/drive.py:176-200`) and its 20-star user base depends on the link surviving. Item 1 under "What is not
  proven" drops from a design risk to a confirmation step on the first scratch run.
- `revisionId` is the wrong change signal: two projects found this independently. gdoc-sync rejects it because
  Google issues new ids without content changes and uses a text fingerprint instead; gdoc uses the Drive `version`
  integer and still records false conflicts when someone only touches formatting in the UI. The push guard
  therefore reads `version`, and on a mismatch exports and compares normalized text to the snapshot; only a real
  content change aborts the push. `revisionId` is not stored at all.
- None of the three does checkboxes, so there is nothing to fork. Build, borrowing three pieces:
  gdoc-sync `src/gdoc_sync/merge.py` (diff3 via `git merge-file` with pure-Python fallback, no Google deps),
  md-gdoc `src/md_gdoc/unescape.py` `clean()` (the escape list), gdoc `gdoc/api/drive.py` `update_doc_content`
  and `export_doc` (the two Drive calls with `fields="version"`).
- Keep `drive.file`; all three take full Drive access, which is the main reason not to adopt any of them as is.

## Background and Setup

Written for the sessions that implement the sync (PT-003 onward). Everything here was established in this
spike; the Evidence and Sources sections hold the proof and links.

### Goal and test case

Two-way sync between a local markdown task list and one native Google Doc. Either side may add a task, edit its
text, or tick it done; the script reconciles both. The script is a reusable single-file Python CLI, not tied to any
repository's conventions. The first proof is a scratch Doc, not a real list.

### What is proven (2026-10-21, through the Google Drive connector, same converter as the API)

- Uploading `text/markdown` creates a native Doc. Checkboxes (`- [ ]`, `- [x]`), nested items, headings, bold,
  italic, inline code, links, tables, footnotes, rules survive. Fenced code blocks do not.
- Exporting as `text/markdown` returns the content, including checkbox state and lines typed or ticked in the Docs
  UI, with deterministic noise (see Normalizer rules). A second round trip is stable.
- Text typed in the Docs UI inherits the formatting of the text before it: T-004, typed after a bold line, came
  back as `**T-004 ...**`. Treat inline bold or italic on a task line as noise unless the local side had it.

### What is not proven (needs real credentials; do these first on a scratch Doc)

1. `files.update` with a `text/markdown` media body replaces a native Doc's content in place and keeps its id and
   link. Google's upload guide lists Markdown as an import format for both create and update, and the gdoc project
   relies on it (see Similar implementations); still confirm on a scratch Doc.
2. The Drive `version` integer from `files.get` moves on every UI edit, including cosmetic ones, so it is a safe
   but noisy push guard; pair it with an export equality check.
3. How the Docs UI exports a checkbox nested under a checkbox at deeper levels (one level exported at 6 spaces).

### Google API facts

- Drive API v3, no Docs API needed for whole-document replace:
  `files.create(body={"name": ..., "mimeType": "application/vnd.google-apps.document"}, media_body=<text/markdown>)`,
  `files.update(fileId, media_body=<text/markdown>)`, `files.export(fileId, mimeType="text/markdown")` (10 MB
  limit), `files.get(fileId, fields="id,modifiedTime,headRevisionId,version")`, `revisions.list(fileId)`.
- The real v3 API queries by `name`; the Claude connector queried by `title`. Do not copy connector syntax into code.
- No API names a version. No API creates a code block. No API inserts HTML into an existing Doc.
- Quotas: Drive 325,000 units/min per user; Docs API 60 writes/min per user. Irrelevant at any sync cadence.
- Docs API `batchUpdate` is the only way to edit part of a Doc. It addresses UTF-16 indexes that shift after every
  insert, so it is the expensive path; see "Whole-document replace" below.

### Auth setup (one time, by a human)

1. Google Cloud console: create a project owned by md2gdoc (decided 2026-10-21). Enable the Google Drive API.
2. OAuth consent screen: user type External. Add the scope `https://www.googleapis.com/auth/drive.file` (the
   script can then only see files it created; no access to the rest of Drive). This scope is non-sensitive, so
   publishing status can be set to "In production" without Google verification. Leave it in "Testing" and refresh
   tokens expire after 7 days, which means a browser login every week.
3. Credentials: create an OAuth client ID of type "Desktop app". Download the JSON as `client_secret.json`. Keep it
   and the generated `token.json` out of git (`.gitignore` both).
4. First run opens a browser once (`InstalledAppFlow.run_local_server`), then the cached token refreshes itself.
5. Syncing a Doc that a human created by hand is outside `drive.file`; either let the script create the Doc or use
   the broader `drive` scope, which is sensitive and needs verification for production status.

### Python

- Single file, PEP 723 inline metadata so `uv run gdoc_sync.py ...` installs deps:
  `google-api-python-client`, `google-auth-oauthlib`, `google-auth-httplib2`.
- Media upload: `googleapiclient.http.MediaIoBaseUpload(io.BytesIO(md.encode()), mimetype="text/markdown")`.

### Script design

- Subcommands: `init` (create the Doc from the markdown file, write the state file), `pull`, `push`, `sync`,
  `status`, each with `--dry-run`. `--help` must explain setup, files, and exit codes.
- State file next to the markdown (for example `tasks.md.gdoc.json`): Doc id, link, Drive `version` at last sync,
  and the normalized snapshot of the last synced content (the merge base).
- Normalizer (applied to both sides before any comparison; export noise observed, all reversible):
  strip `**` wrapping a heading; unescape `\-`, `\[`, `\]`, `\#`, `\_`, `\<`, `\:`, `\*`; collapse an autolink
  `[url](url)` to `url`; drop two trailing spaces on list items; re-indent nested items to 4 spaces per level
  (export gives 2 for plain items, 6 for a nested checkbox); restore the final newline; join nothing (soft line
  breaks are already joined by Docs, so keep one logical line per task).
- Merge: three-way on normalized lines, base = snapshot, ours = local file, theirs = Doc export. Added lines on
  either side are kept; a line changed on one side only takes that change; a checkbox ticked on one side wins
  over an untouched box.
- True conflict (same line changed differently on both sides): keep both lines, marked
  `<<<<<<< api-edited` ... `=======` ... `>>>>>>> hand-edited`, exit code 2, no push.
- Push guard: before `files.update`, re-read the Drive `version`; if it differs from the one pulled, export again
  and compare normalized text to the snapshot; abort only if the content moved. Skip the push when the normalized
  content is unchanged, so no empty revisions. Do not use `revisionId` (see Similar implementations).
- After a successful push, pull once more and store the new `version` and snapshot.

### Whole-document replace: must every push replace the Doc?

Not necessarily, but the alternative is costly. Options, in order of effort:

a. Whole replace via `files.update` (recommended for v1): one call, deterministic. Side effects: comments and
   suggestions anchored in the Doc are lost on the next push, manual formatting in the Doc is lost, and version
   history gains one unnamed revision per push (skipping no-op pushes limits this).
b. Targeted edits via Docs API `batchUpdate`: pull the document JSON, map paragraphs to markdown lines, delete and
   insert only the changed paragraphs, re-apply the checkbox bullet. Untouched paragraphs keep their comments.
   Whether the Docs API can set a checkbox's checked state is unverified; if it cannot, option b cannot tick a box
   and would need to be combined with a. Expect several days of work and index arithmetic bugs.
c. Hybrid: b for small diffs, a when the diff is large or b fails. Needs b first.
