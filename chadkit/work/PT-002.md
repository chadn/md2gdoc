## Answers (2026-10-21)

Tested through the Google Drive connector attached to Claude Code; API facts from Google's docs (Sources).

1. **Markdown coverage.** Writing: uploading `text/markdown` converts to a native Doc and keeps H1-H6, bold, italic,
   inline code, links, nested bullet and numbered lists (a list starting at 5 keeps its start), tables with bold
   cells, blockquotes (as an indented paragraph), horizontal rules, checkboxes, and footnotes (real Docs footnotes).
   Fenced code blocks are lost: the lines become plain Arial body paragraphs with blank lines between them, and
   indented code loses its indent. Reading: `text/markdown` export returns the content with these changes: every
   heading comes back wrapped in `**`, `-` inside text is escaped as `\-`, soft line breaks are joined into one
   line, `_italic_` becomes `*italic*`, 4-space nesting becomes 2-space, list items gain two trailing spaces, the
   final newline is dropped. A second round trip is stable except the code indent.
2. **HTML blocks.** Raw `<div style="color:red">` inside markdown survives as red text, so inline styles do apply.
   `<details>` is destructive: its text merged into the next heading. A whole-document `text/html` upload keeps
   headings, bold, italic, links, tables, strikethrough, underline, inline color and background, and images, but
   nested `<ul>` loses its nesting, `<pre><code>` becomes per-line inline monospace rather than a block,
   `<blockquote>` becomes a plain paragraph, and `<sup>` is lost on export. No API inserts HTML into an existing
   Doc; HTML only enters through conversion on upload. The native "Code blocks" building block is UI only, paid
   Workspace editions only, and no Docs API request creates one.
3. **Two-way sync.** Possible only as semantic sync, never byte sync. Every pull reformats the markdown (item 1): on
   a 45-line resume-style sample with zero content change, the round trip changed about 30 lines. A sync would need
   a normalizer (strip heading bold, unescape `\-`, re-nest to 4 spaces, drop trailing spaces, restore soft breaks)
   and conflict detection on normalized text, and an edit made in Docs has no guaranteed mapping to one markdown
   line. This is the familiar fight with a formatter that rewrites untouched lines. Through this session's connector
   a push is create-a-new-file: Drive `update_file` is metadata only, so the link changes each push unless the Docs
   connector is attached (it is not, here) or a script calls `files.update` with `text/markdown` directly. One-way
   push with Docs as a read-only copy is cheap and reliable; a resume-style document uses only features that survive
   (fixture 03: headings, nested lists, rules, bold labels; no code blocks, tables, HTML, links, or footnotes).
4. **Named versions.** No. The Drive v3 Revision resource has no name field, the Docs API and Apps Script have no
   version methods, and `keepForever` applies only to binary files. `revisions.list` works for Docs (Google warns
   it may be incomplete). This connector's download accepts a `revisionId` but exposes no way to list revisions.
   Substitutes: a `files.copy` snapshot titled with the version, or the `Version:` line already in the document.
5. **Paths.** See Options and Comparison of the top 3.

## Recommendation

Try first: **C, own script, one-way push** from the repo to one native Doc.

- why: the only path that keeps one link, runs from a git hook or cron with no LLM in the loop, and is deterministic;
  a resume-style document uses only features the converter keeps, so the Doc matches the repo after every push.
- why not: one-time OAuth setup and a refresh token to keep safe; the in-place markdown update is documented but
  untested, so step one is proving it on a scratch Doc; adding fenced code to a synced file later would silently
  degrade in the Doc.
- side effects: every push overwrites the Doc, so edits made in Docs are lost unless pulled and merged first; version
  history gains one unnamed revision per push.

Try second, only if interactive AI editing of other Docs matters: **B, the Google Docs connector** on claude.ai.

- why: the only path where Claude edits an existing Doc in place and can propose suggestions instead of overwriting.
- why not: non-deterministic; the skill reference lists many failure modes (stale indexes, headings losing bold,
  typed list markers); not usable from Claude Code; eligibility by plan is not published.
- side effects: enabling it grants Claude write access to every Doc in the account; a wrong batch lands in the real
  file, mitigated only by the revision guard and version history.

Not recommended on its own: **A**. Create-only, so each push makes a new link. Keep it as the zero-setup read path
and for one-off creates.
