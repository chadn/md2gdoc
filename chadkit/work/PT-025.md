# PT-025 - Windows, macOS and Linux

Built 2026-10-22 to [PD-002](../decisions/PD-002-architecture-direction.md) Platforms. In
[md2gdoc.py](../../md2gdoc.py): the markdown file is read with Python's universal newlines, so the text layer sees
`\n` whatever the file holds, and `write_md()` writes it back with CRLF when the file has a CRLF today, else LF, on
every platform; the state file is always written LF, since it is committed and a Windows checkout must not rewrite
it; `cli()` reconfigures stdout and stderr to UTF-8, so a diff with non-ASCII text prints under any console code
page. Pinned in [tests/test_cli.py](../../tests/test_cli.py): a CRLF copy of fixture 04 goes through `init` with an
LF push form and an LF state file, a `pull` writes it back all CRLF and `status` reads it unchanged, and an LF file
stays LF. The config directory on Windows is PT-020's, pinned there.

[.github/workflows/tests.yml](../../.github/workflows/tests.yml) runs the tests on Ubuntu, macOS and Windows with
Python 3.11, 3.13 and 3.14 on every push to GitHub and every pull request, with no Google access.
[.gitattributes](../../.gitattributes) makes every text file LF in every checkout, so the state files are not
rewritten by git on Windows, and leaves the fixtures and the evidence folders untouched either way, so an export
that comes back with a CRLF stays as returned; Git for Windows installs with `autocrlf=true` by default, the GitHub
runner's image does not set it (the gate, PLR-20261022-13), so the attribute is for the person's checkout.

Decisions taken here: CRLF is detected from the file's bytes at write time rather than carried through the state,
since the file is the only place the choice lives and `pull --force` onto a CRLF file should keep it CRLF; a file
with mixed endings comes back all CRLF and a CR-only file comes back LF, the two edges the rule has; the tests read
and write every file as UTF-8 by name, since Windows decodes with the console code page otherwise and fixture 03
holds non-ASCII (the gate's simulation under cp1252); no CI for the gate checks, which need the chadkit CLI, and
none for a real Google run, which PD-002 keeps out of CI until a service-account path exists.

Not done: a Windows run of anything here (the CI is it); the install under Windows (`md2gdoc.exe` as the program
name is argparse's default and unverified, PLR-20261022-12); a UTF-8 byte order mark at the start of a file, which
`read_md` keeps and the push form would send (the gate, PLR-20261022-13; a later task if a Windows editor writes one).
