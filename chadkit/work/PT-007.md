# PT-007 - sync: the three-way merge

Built in [md2gdoc.py](../../md2gdoc.py) as `merge3()` and `cmd_sync()` under the design's "Script design" Merge, True
conflict and Push guard bullets, tested against the fake Drive in [tests/test_cli.py](../../tests/test_cli.py) (the
`Sync` and `Merge` cases), and run for real on 2026-10-22 under `uv run --script` on a scratch copy of fixture 04,
with the token in a scratch profile folder so no browser opened: [PT-007/real-run.out.txt](PT-007/real-run.out.txt)
is that transcript as printed, the Doc trashed at the end. The Doc-side edits were made outside the script by
[PT-007/outside.py](PT-007/outside.py), which exports, normalizes, edits and sends the push form, the closest the
API comes to a UI edit. The transcript is of the code as committed, re-run after the gate's findings were applied.

What the real run showed, in order: `sync` on a fresh Doc reports in sync and exports once; with a tick and a
reword in the file and a tick and a new item in the Doc, `sync --dry-run` prints the merge as two diffs, one per
side, and `sync` writes the file and pushes the Doc (version 9), after which `status` reads both sides unchanged;
the same line edited differently on both sides is written to the file between `<<<<<<< api-edited` and
`>>>>>>> hand-edited` with exit 2 and nothing pushed; a second `sync` refuses the file while it holds the markers;
resolved by hand to the Doc's version, `sync` pulls and has nothing to push. The first attempt at the transcript
inserted the new item after a blank line, which makes the list loose, and the Doc came back with a blank line
after every item; that is the converter, not the merge (the
[loose-list probe](PT-007/loose-list-probe.out.txt); the script's own cycle is stable over three round trips, the
[round-trips probe](PT-007/roundtrips-probe.out.txt)), recorded as an `idea` row in
[docs/features.md](../../docs/features.md).

Decisions taken here:

- The base is `snapshot`, the Doc's normalized text at the last sync, as design.md says; `local` stays the no-op
  test only (PT-006's open question). A converter difference between the two shows up as a one-sided change on
  the file's side and the file's form wins, so the file never inherits the Doc's blank line before a list.
- Pure Python on `difflib` matching blocks, not `git merge-file` with a fallback as gdoc-sync does: one code path
  that runs the same everywhere, and git is not a given on every desktop (PG-02).
- Three rules beyond diff3, each chosen because no line is lost: an equal-length chunk changed on both sides is
  merged line by line, so a box ticked on each of two neighbouring lines is no conflict (diff3 and git would stop);
  lines one side added right before or after a chunk the other side changed are kept around the change; lines
  both sides added at the same place are all kept, the file's first. Everything else that differs on both sides is
  a conflict, a deletion against an edit included.
- A conflict is written to the file, like git, so both versions sit where the user edits; `--dry-run` prints it
  instead. A file that still holds a `<<<<<<< api-edited` or `>>>>>>> hand-edited` line is refused with exit 2 (the
  `=======` line alone is not a marker, since a setext heading underline looks the same).
- The push guard is a second export right before the push, compared to the one the merge read, as `push` does;
  a Doc that changed meanwhile refuses the push with exit 3, the merge already written to the file waiting for the
  next run (a unit test fakes it; not seen live). The Drive `version` plays no part: the gate showed that a
  version read before the push cannot see a UI edit that lands between the export and the push, since the version
  lags such an edit by about 100 seconds (PT-018), so the first build's version-then-export guard lost that edit
  silently (PLR-20261022-10). The task line's "`version` push guard" is met by the export, as design.md item 2
  allows; the version is read once for the state file.
- When one side is unchanged since the last sync, the other side is the result and no merge runs: the gate showed
  that the converter's own difference between `snapshot` and `local` (the blank line before a list) read as a
  conflict when the Doc edited the paragraph above it.
- `push` refuses a file holding markers too, so markers reach the Doc by no path.
- The file is written only when the merge changed it, and then in normalized form, as `pull` writes it.

Not done: `--json` output (PT-026); the real list, this repository's tasks.md (PT-008); a line-level merge of a
chunk whose line count changed on one side, which is a conflict today.
