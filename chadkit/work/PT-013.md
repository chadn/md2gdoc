# PT-013 - Code blocks through Google Docs

Spike: find a treatment for code that is better than `not possible`. Names used here and in `docs/features.md`:
single backtick is inline code, triple backtick is a fenced code block; indented code is the four-space form.

## What is known (PT-002, fixture 01)

- Inline code survives the round trip as a monospace run.
- A fenced block's lines come back as plain Arial paragraphs with blank lines between them; the fence is gone.
- Indented code loses its indent.
- The native "Code blocks" building block is UI only, paid Workspace editions only, and no Docs API request
  creates one.

## Candidates to test

1. Monospace runs: push each code line as a paragraph in a monospace font and let the normalizer turn
   consecutive monospace paragraphs back into a fence (md-gdoc's `clean()` does this on pull).
2. A marker the normalizer restores: push the fence as literal text the converter keeps, strip it on pull.
3. Docs API `batchUpdate` after the push to restyle the block (needs PT-009's machinery).
4. Whatever the Docs UI export emits for a hand-made Code block, if one is made by hand once.

## Open

- Edge cases for inline code: backticks inside, code at line start, code in a table cell or task line.
- Whether a `workaround` status in `docs/features.md` is earned: partial fidelity with the loss written down.

Closes by promotion: a task per candidate that works, a `t_lesson` for what does not, rows in features.md.
