# PT-013 - Code blocks through Google Docs

Spike: find a treatment for code that is better than `not possible`. Names used here and in `docs/features.md`:
single backtick is inline code, triple backtick is a fenced code block; indented code is the four-space form.
Closed 2026-10-21 by promotion: the treatment is specified under "Push form" and the code-run fold in
`docs/design.md`, pinned by fixture 05, built by PT-005; the rows in `docs/features.md` carry the statuses.

## Method

Seven scratch Docs made through the claude.ai Drive connector (markdown or HTML upload with conversion, then the
`text/markdown` export), as PT-002 did. Six are trashed; fixture 05's Doc is kept so a person can see how a
code run looks in the Docs UI: https://docs.google.com/document/d/1p_UP6HcB5zF2okKbLIWcZUl1O4ofnOuTLWTOx4ikuyE
(its first upload, with a long first paragraph and an unpadded backtick line, is trashed). The exports were read
byte for byte with whitespace made visible.

## Answers

1. Inline code is safe. Backticks inside (``a `b` c``), `*`, `_`, `<tag>`, `**`, code in a table cell, at the
   start of a task line, next to bold or italic, and an escaped backtick all come back unchanged (fixture 05).
2. A raw fence is not. Backtick and tilde fences lose the fence and the language; each line becomes a plain
   paragraph; markdown-looking lines inside (`#`, `-`, `>`, `1.`) come back escaped, which the normalizer already
   unescapes; a fence inside a list item becomes continuation paragraphs with whitespace-only lines (probe 1).
3. A *code run* survives: one code span per line, lines joined by hard breaks (two trailing spaces). Google
   imports it as a monospace paragraph and exports it in the same shape, so the shape is a fixed point.
   Lines joined by soft breaks collapse into one line instead (probe 2).
4. Indentation needs entities. Leading spaces or a tab outside the span are stripped by the import (continuation
   lines lose leading whitespace); inside the span the export moves them outside, and the next import strips
   them. `&nbsp;` and `&#9;` outside the span import as the characters and export as plain spaces or a tab in
   front of the span, which is what a pull needs (probes 2, 4, 6; fixture 05). A raw NBSP in prose exports as
   NBSP; in front of a code span it exports as spaces.
5. A blank line inside the block travels as `&nbsp;` plus the hard break and exports as a whitespace-only line
   that still sits inside the run (fixture 05). A `` ` ` `` span does the same but reads worse.
6. Trailing whitespace inside a code line is moved outside the span on export (fixture 05 line 27 shows it for
   the pad space; probe 4 for three real spaces) and lost on the next import. An entity was not tried.
7. The language tag has no representation in the Doc. The fold takes it from the local file's block at the same
   position; a fresh pull without a local file yields a bare fence.
8. HTML import of `<pre><code>` keeps indentation and exports as code spans, but only when the HTML carries an
   `<html><body>` wrapper (probe 5); a bare fragment exports as plain paragraphs (probe 3). `<p>` or `<span>` in
   Courier New or a generic monospace font exports as plain text, so the exporter keys on the import's own code
   style, not on the font. The HTML path turns lists into blockquoted lists and drops the blockquote marker
   anyway (fixture 02), so it is not the push route.
9. Markers restored on pull (escaped fences, `CODE-BEGIN`) import as prose and are pointless once the code run
   works (probe 2).

## Candidates, settled

1. Monospace runs: works, as the code run in the push form. Promoted into PT-005 and `docs/design.md`.
2. Marker restored by the normalizer: dropped (answer 9).
3. `batchUpdate` restyle after the push: deferred with PT-009; it could add a background or the Code block style
   if the Docs API ever exposes one.
4. Hand-made Code block export: cannot be tried here; the building block is UI only on paid Workspace editions
   and this account is a personal one. `not possible` in `docs/features.md`.

## Open

- Fenced code inside a list item: probe 6 showed a code run inside an item keeps its lines in the item with the
  item's indent, and a task line with a code run below it exports with a 6-space indent. No fixture pins it; add
  one when a synced file needs it.
- Indented code (four spaces) in a source file: the import drops the indent and makes plain paragraphs. The
  normalizer could rewrite it to a fence before the push; nobody has asked.
- How a code run looks in the Docs UI (monospace lines, no background is the expectation) is unverified until a
  person opens the fixture 05 Doc.
