# PT-013 - Code blocks through Google Docs

Summary: only inline code (single backtick) works, not fenced code block (triple backtick).
A workaround has been tested for fenced code block, so still can use.

A fenced code block sent to Google as written comes back as plain paragraphs: fence, language and indentation
gone. Sent as a _code run_, one code span per line with a hard break (two trailing spaces) after every line but
the last, it comes back in that same shape, and the pull folds it into the fence again. That is the treatment,
closed 2026-10-21 by promotion: PT-005 built it in [md2gdoc.py](../../md2gdoc.py) (`push_form()` makes the run,
`normalize()` folds it back), fixture 05 below proves it, and the code rows in
[docs/features.md](../../docs/features.md) carry the statuses.

What it costs: in the Doc the block is monospace
lines with no background; the language tag, the fence style and a trailing blank line are not in the Doc (the
tag comes back from the local file); trailing whitespace inside a code line is lost. Not solved, `idea` rows: a
fence indented under a list item, and indented (four-space) code.

## The example, end to end

Fixture 05 is one file through the whole path; its `python` block is shown at each step. A hard break is two
spaces at the end of a line, invisible on this page; the files have them.

### 1. The file a person writes

[05-code-blocks.src.md](../../tests/fixtures/05-code-blocks.src.md), lines 15 to 20:

````markdown
```python
def hello():
    return "world"

print(hello())
```
````

### 2. What the script sends in its place: the push form

[05-code-blocks.in.md](../../tests/fixtures/05-code-blocks.in.md), lines 15 to 18. `push_form()` turned the
block into a code run; the leading spaces became `&nbsp;` entities and the blank line one `&nbsp;`, because the
import strips real leading whitespace from a continuation line (probe 2). The rest of the file is sent as
written.

```text
`def hello():`  
&nbsp;&nbsp;&nbsp;&nbsp;`return "world"`  
&nbsp;  
`print(hello())`
```

### 3. The Doc Google makes

[Google Doc: md2gdoc fixture 05 code
blocks](https://docs.google.com/document/d/1p_UP6HcB5zF2okKbLIWcZUl1O4ofnOuTLWTOx4ikuyE),
kept so a person can look: the run is one paragraph of monospace lines with no background (seen 2026-10-22).
The six probe Docs are trashed; their uploads and exports, as the connector sent and returned them, were
recovered from this session's transcript into the probe files under [PT-013/](PT-013/), listed below.

### 4. What Google exports

[05-code-blocks.out.md](../../tests/fixtures/05-code-blocks.out.md), lines 15 to 18: the entities came back as
real spaces outside the spans and the hard breaks stayed, so the shape is a fixed point.

```text
`def hello():`  
    `return "world"`  
   
`print(hello())`
```

### 5. What the pull writes

`normalize(out, src)` returns the source file byte for byte, `python` tag included, since the tag is taken from
the local file's block at the same position; a pull with no local file gives the same text with a bare fence.
The test is `CodeBlocks` in [tests/test_normalize.py](../../tests/test_normalize.py).

## Candidates, settled

1. Monospace runs: works, as the code run in the push form. Promoted into PT-005 and
   [docs/design.md](../../docs/design.md).
2. A marker the normalizer restores: dropped, the converter joins it into prose (probe 2).
3. `batchUpdate` restyle after the push: deferred with PT-009; it could add a background or the Code block style
   if the Docs API ever exposes one.
4. Hand-made Code block export: cannot be tried here; the building block is UI only on paid Workspace editions
   and this account is a personal one. `not possible` in [docs/features.md](../../docs/features.md).

## Open

- Fenced code inside a list item: sent as it is today and loses its shape (probe 1). A code run inside an item
  keeps its lines in the item (probe 6), so the push form could build one; nobody has asked.
- Indented code (four spaces): the import drops the indent (probe 1). The push form could rewrite it to a fence;
  nobody has asked.
- Raw non-breaking space characters were not tested: probe 4's "NBSP" sections carried plain spaces. The push
  form uses entities, which probe 6 and fixture 05 cover.
