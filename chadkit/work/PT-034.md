# PT-034 - The file's side survives a Doc-only change

A _Doc-only change_: a sync or pull where the file has not changed since the last sync and the Doc has. Found
2026-10-29 in use on another repository's file: a file with an HTML comment at its top was pushed, edited in the
Doc, and synced; the comment was gone from the file, and lines the Doc had not touched came back in the export's
shape. The run's output was not kept; fixture 15 is the evidence. Status: completed 2026-10-30, with PT-031's footer
folded in. The design is in [docs/design.md](../../docs/design.md), "Two forms" and "Footer"; this file holds the
cause, the evidence, the decisions and what is left open.

## Cause

`cmd_sync` in [md2gdoc.py](../../md2gdoc.py) took the Doc's export as the result of a Doc-only change, nothing
merged, so that the converter's own differences between the two texts of the last sync never read as a conflict.
`cmd_pull` and the attach (`init --doc`) wrote the export over the file the same way. The price: everything Google's
import drops was lost, and every untouched line took the export's form. Fixture 15 pins what the import does to such
a file: a whole-line HTML comment block is dropped, a resolved task line `[-]` comes back as an open box `[ ]`, a
lazy continuation line under a list item comes back indented by two, and a list right after a paragraph gets a
blank line before it. The normalizer keeps an HTML comment, so the file side had it and the Doc side never did; a
line starting with `<` reads as kind `other` to the edit path, so a push of a file with a comment line was a whole
replace (`structure`) as well.

## Evidence

- Fixture 15, made by [probe.py](PT-034/probe.py) ([probe.out.txt](PT-034/probe.out.txt)); the
  [`documents.get` probe](PT-034/probe-paragraphs.py) ([its output](PT-034/probe-paragraphs.out.txt)) shows Google
  puts an empty paragraph between a paragraph and the list that follows it, so the fake Drive in the tests adds that
  blank on import, as Google does, not on export as it did; it also indents a lazy continuation line and opens a
  `[-]` box on import, as fixture 15 shows.
- Tests: `Forms` (unit), `FileSide` and `Footer` (commands) in [tests/test_cli.py](../../tests/test_cli.py);
  `HtmlComment` in [tests/test_normalize.py](../../tests/test_normalize.py). 121 tests pass.
- Live, [live.out.txt](PT-034/live.out.txt): this repository's task list took its footer on both sides by 16 edits
  and read in sync after; after the gate's fixes, a Doc-side edit made through the Docs API
  ([live-edit.py](PT-034/live-edit.py)) came into the file by a sync that pushed nothing, with the `[-]` PT-031 line
  and the one footer intact; the file edited back pushed by 8 edits, and the next sync read in sync. `chadkit
  validate` and `chadkit doctor` accept the footer.

## Decided here

- The footer PT-031 asked for ([chadkit/work/PT-031.md](PT-031.md)): three paragraphs separated by blank lines
  (two prose lines in a row send the edit path to the whole replace), the time in the machine's zone as
  `YYYY-MM-DD HH:MMam|pm TZ`, the path from the repository root as a code span (a bare path with a `_` reads as
  italics to the edit path), the Doc's link. The time is of the last command that wrote that side: the Doc's footer
  is not refreshed for the time alone, since a Doc-only change or a comment-only edit would otherwise write the Doc
  on every run, by the whole replace where a line forces it. `--no-footer` on `init`, `pull`, `push` or `sync`, kept
  in the state file from that command on.
- A footer is recognized by its three shapes wherever it sits, so a task line `chadkit task add` appends after it
  stays body and the footer moves back to the end; the gate found that `chadkit task add` appends at the end of the
  file, which would have left two footers for good.
- `pull --force` writes the Doc's text as it is, changed file or not. The attach writes the file only, and the Doc's
  footer moves only with a write for a change, so an attached Doc the edit path cannot map is never replaced for
  the footer alone. The second pass found a path with a space never recognized, two footers and a replace per
  sync; the path line now matches on its dot or slash, spaces allowed, with a test.
- The gate's first pass found `replay()` dropping the unchanged lines of a converter-rewritten run, and a comment, when
  the Doc edited a line in or beside such a run; the alignment is now line by line on the text stripped of the
  converter's reshaping, a hunk at an unpaired run carries the run's unchanged lines along, and a comment a hunk
  spans is kept after it.

## Left open

- The lines right around a change take the changed side's shape (a Doc edit next to a lazy continuation line
  indents that line in the file; a Doc edit of a `[-]` line's text reopens it as `[ ]`, since the Doc holds `[ ]`).
- A paragraph with soft breaks in it, a lazy continuation line included, is a Doc paragraph with U+000B breaks,
  which the edit path refuses (`structure`, the known Shift+Enter case in [docs/features.md](../../docs/features.md)),
  so a file like the one found pushes by the whole replace whatever its comments; not this task's.
- Whether the export puts a blank line before a list that an edit, not the import, placed right after a paragraph is
  unmeasured; the fake Drive assumes not.
- A `[-]` line beside checkbox lines still sends every push to the whole replace (`layout`); no task owns it.
- A comment that starts mid-line, one never closed, or one inside a fence is prose or code and goes to the Doc as
  such; not tried through the import.
- On Windows the footer's zone is the long name the machine gives (`Pacific Daylight Time`); not run there.
- In the `Footer` tests every Doc write after the first is a whole replace (`inline`): the fake keeps no code span
  on an inserted line and the temporary folder's path holds a `_`; the edits path for the footer is shown by the
  live run alone.

Done: a Doc-only change on a file with an HTML comment and a footer leaves both in the file (`FileSide`, `Footer`),
a file-only change pushes the file's hunks and not the file's shape of untouched lines (`FileSide`), the fixture pair
is in, and this repository's task list synced after a live Doc-side edit with PT-031 still `[-]` (live.out.txt).
