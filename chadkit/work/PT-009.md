# PT-009 Targeted edits through the Docs API

What the Docs API can and cannot do for a sync that edits a Doc in place instead of replacing it, measured on
scratch Docs made by the script's own profile (2026-10-25 and 2026-10-26, all trashed after). The task's build is
not started; this file is the evidence Chad's decision rests on.

## The first step, 2026-10-25: can a request set a checkbox's state? No.

Three probes on one Doc made by the script from `- [ ] unticked`, `- [x] ticked`, `- plain bullet`, `Text.`:

1. [probe-1-dump.py](PT-009/probe-1-dump.py) (printed to the terminal, output not kept) and
   [probe-2-docjson.py](PT-009/probe-2-docjson.py) ([output](PT-009/probe-2-docjson.out.txt), captured after
   probe 3 had run, so `unticked` carries the strikethrough probe 3 set): in `documents.get`, the ticked paragraph
   and the unticked `added after ticked` are identical, the same `listId`, an empty `textStyle`, no other field.
   The checklist's `NestingLevel` has `glyphType: GLYPH_TYPE_UNSPECIFIED` and no `glyphSymbol`. Nothing in the
   document JSON carries the state that the markdown export shows as `[x]`.
2. The API: `Bullet` has `listId`, `nestingLevel`, `textStyle` and nothing else; `NestingLevel` has no checked
   field; `GlyphType` has no checkbox value; of the 53 `batchUpdate` request types the only checkbox-related one is
   `createParagraphBullets` with `bulletPreset: BULLET_CHECKBOX`, which makes boxes, not ticks
   ([probe-10-discovery.py](PT-009/probe-10-discovery.py), [output](PT-009/probe-10-discovery.out.txt), the
   discovery document at revision 20261021).
3. [probe-3-edits.py](PT-009/probe-3-edits.py) ([output](PT-009/probe-3-edits.out.txt)), the three edits that
   could have carried a state, each read back through the markdown export: `updateTextStyle` strikethrough on the
   unticked item gives `- [ ] ~~unticked~~`, not a tick; `insertText` of a new paragraph after the ticked item
   gives `- [ ] added after ticked`, the state not inherited; `createParagraphBullets` with `BULLET_CHECKBOX` on
   `Text.` gives `- [ ] Text.`.

The markdown import and export are the only paths that carry checkbox state, and the import is whole-document.

### How the import shapes a Doc (probe 4)

| Markdown | In `documents.get` |
|---|---|
| Heading | one paragraph, `namedStyleType: HEADING_n` |
| Paragraph with inline styles | one paragraph, a text run per style change; a code span is `Roboto Mono` plus a green foreground; a link is `link.url` plus underline and blue |
| List item | one paragraph with `bullet.listId` and `nestingLevel` (absent at level 0, probes 6 and 7), `indentStart` 36 PT per level; a nested item is the same list, deeper level |
| Checklist | a list whose `glyphType` is `GLYPH_TYPE_UNSPECIFIED`, no `glyphSymbol`; ticked and unticked identical |
| Blockquote | paragraphs with `indentStart`, `indentFirstLine` and `indentEnd` of 30 PT, an empty one before the quote |
| Fenced code (sent as a code run) | one paragraph for the block, its lines joined by U+000B, `Roboto Mono` green runs |
| Rule `---` | a `horizontalRule` paragraph element, 1 index wide, in a paragraph of 2 |
| Table | a `table` structural element; each cell holds its own paragraphs, so a 2x2 table is four more paragraphs |
| Blank line | an empty paragraph with `indentStart` 0; the import writes one between two prose paragraphs (probe 5), before a quote, around a code block and a rule, after a table, none after a heading or between lists; API edits write none |
| Emoji | two UTF-16 code units; every index in a request counts that way |

### What works as it stands

| Edit | How | Evidence |
|---|---|---|
| Change a word inside a paragraph | `deleteContentRange` plus `insertText` at the word; bold, italic, code span and link runs elsewhere in the paragraph keep their style; a comment anchored on another word of the paragraph stays | probe 6b step a, probe 5 (Alpha) |
| Insert text after an emoji | index in UTF-16 code units (`len(s.encode("utf-16-le")) // 2`): Python index 70, request index 71 | probe 6b step a |
| Replace a heading's text | delete to the newline, insert; the paragraph stays `HEADING_1` | probe 6 step b |
| Change a heading's level | `updateParagraphStyle` `namedStyleType` | probe 6b step k |
| Delete a paragraph | `deleteContentRange` over its range including the newline; its comment is orphaned, as under a whole replace | probe 6 step e, probe 5 (Beta) |
| Add an item to a list | `insertText` of `\n` plus the text inside the neighbouring item; the new paragraph inherits the bullet at the neighbour's level | probe 6 step d |
| A link | `updateTextStyle` with `link.url`; the export writes `[text](url)` | probe 6 step f |
| A code line | `updateTextStyle` with `weightedFontFamily` `Roboto Mono`; the font alone makes the export write a code span, the green is not needed | probe 6 step f |
| A table | `insertTable`, then `insertText` at each cell's first paragraph; the export writes a markdown table | probe 6 step g |
| A blockquote | `updateParagraphStyle` with the three 30 PT indents; the export writes `>` | probe 6 step i |
| An image | `insertInlineImage` from a public URL; the export writes the data URI form fixture 11 shows | probe 6 step j |
| A nested list, made fresh | `insertText` of the items with one leading tab per level, indents zeroed, one `createParagraphBullets` over the whole range; levels 0, 1, 2 come back | probe 7 |
| A concurrency guard | `writeControl.requiredRevisionId` from `documents.get`; a stale id is refused with 400 "does not match the latest revision" | probe 6b step o |
| Edits as suggestions | `writeControl.writeMode: SUGGEST` on an `insertText`, under the default profile's `drive.file` token ([PT-022.md](PT-022.md); the probe does not print the scope); the run carries `suggestedInsertionIds` | probe 6b step p |
| Read comments and their anchors | `documents.get` with `includeTabsContent`, `suggestionsViewMode: SUGGESTIONS_INLINE` and `commentsViewMode: COMMENTS_VIEW_MODE_INCLUDED` (the API refuses each without the one before, with a 400 that says so; the kept output is the run that passed); `comments[]` with `anchorId`, `tabs[0].documentTab.commentAnchors` with the ranges; a comment whose anchor is missing is orphaned | probe 8 |
| Anchor a new comment | `insertComment` with a `range`, authored as the token's user, `plainTextQuote` filled; the `.docx` export and Drive `comments.list` both show it | probe 8 |

### What works with a second request

| Edit | What happens alone | The fix-up | Evidence |
|---|---|---|---|
| A paragraph after a heading | inherits `HEADING_2` and exports as a heading | `updateParagraphStyle` to `NORMAL_TEXT` | probe 6 step c |
| A paragraph after a list | inherits the bullet | `deleteParagraphBullets` on it | probe 6 step d |
| Nest an item of an existing list | `createParagraphBullets` on that paragraph joins the list at level 0 whatever its tabs or indents; the tab stays as text when the paragraph already had a bullet, is consumed when it had none; indenting it 72 PT changes nothing; any `createParagraphBullets` on a member resets the list's glyphs, `-` came back `*` on every item, a text change the sync would then see | drop the bullets of the whole list, re-insert the tabs, zero the indents, one `createParagraphBullets` over the list | probe 6 step d, probe 6b step d2, probe 9, probe 9b |

### What does not work

| Edit | Finding | Evidence |
|---|---|---|
| Tick or untick a checkbox | no field or request carries the state | the first step above |
| A horizontal rule | `HorizontalRule` is a paragraph element with no insert request among the 53; `---` typed is text and exports as `\---` | probe 6 step i, probe 10 |
| A list's start number | `NestingLevel.startNumber` is output only; no request sets list properties | probe 10 |
| The Drive `version` as a guard | after a `batchUpdate` it still read 10 at 50 seconds and 11 at 110; a Docs-API write must guard on `revisionId` instead, which the Drive push cannot use (PD-001) | probe 7 |
| Paragraphs as lines | the rich Doc had 29 paragraphs outside its table cells for 46 export lines (code lines share a paragraph, a table is many, blank lines are paragraphs only after an import); plain prose maps one to one after an import (9 to 9) and not after API edits (5 paragraphs, 9 lines) | probe 6b step r, probe 5 |

### Comments, formatting and suggestions under each kind of push (probe 5, probe 6b step r, probe 8)

| | Targeted edits | The script's whole replace |
|---|---|---|
| Comment on an untouched paragraph | kept, anchored | orphaned: still listed by Drive `comments.list` and the Docs API with its `anchorId`, no anchor in the Doc, gone from the `.docx` export |
| Comment on an untouched word of an edited paragraph | kept, anchored | orphaned |
| Comment on a paragraph whose text is replaced whole | gone from the `.docx` export; Drive still lists it | orphaned |
| Comment on a deleted paragraph | gone from the `.docx` export; Drive still lists it | orphaned |
| A red word (set in the `.docx`) | kept | gone |
| A highlight set by `updateTextStyle` | not measured | gone |
| A pending suggestion | kept | gone |

Drive `comments.list` never changed through any of it: it cannot tell an anchored comment from an orphaned one.
A pending suggestion appears in the markdown export as accepted text, so `pull` reads an unaccepted suggestion
as content.

Two clauses of PD-001 now have measurements, for Chad to amend or not: C' says whether a checkbox's state can be
set is unverified, and it cannot be; the consequences say comments are "lost", and the measured shape is orphaned,
which a person sees in the Doc's comment list without a highlight (the UI itself was not checked).

### For a tick

| Workaround | Result | Evidence |
|---|---|---|
| Whole replace for the sync whose diff flips a box, the hybrid's fallback | works; that push orphans the Doc's comments and drops suggestions and formatting, as every push does today | probe 5, probe 6b step r |
| Carry the comments over that replace: read each open comment's anchored text and replies through the Docs API, replace, `insertComment` at the text, `addCommentReply` for each reply, `deleteComment` the orphan | works for comments the API made: both comments and the reply came back anchored on their words, the orphans deleted; the new threads are authored by the token's user with the original author named in the body; a comment whose text the push changed or removed would have no place, the probe's logic, not measured (the `BETA ` anchor's trailing space is the probe's own range) | probe 14b |
| A `.docx` body instead of markdown: export the `.docx`, which carries comments and formatting, edit it with python-docx, send it through `files.update` | a changed word, a new paragraph, the comment's anchor and the red word all survive and the Drive `version` moves at once; but the checklist comes back as plain bullets even when the `.docx` is sent back unchanged, and each round trip adds a copy of the comment, 7 after 6 trips, one anchored `Commented` in each `.docx` export | probe 11, probe 14 |
| Word's checkbox forms in that `.docx`: level text U+2610 or U+2611, MS Gothic, Wingdings F0A8, a `w14:checkbox` content control | none imports as a Docs checklist: a glyph becomes the list's bullet symbol and exports as `*`, the control becomes the text U+2612 | probe 12 |
| Strikethrough as the tick | the export writes `- [ ] ~~text~~`, a convention beside the `[x]` the import writes, not in place of it | probe 3 |
| A ballot character as text | U+2612 in a content control came back as text, not a checkbox; whether the UI offers anything on such text was not checked | probe 12 |

No workaround ticks a box in place. For a task list the compromise is the fallback, with or without the carry-over.

### For the rest

| Cannot | Workaround | Evidence |
|---|---|---|
| Insert a horizontal rule | none in place: an empty paragraph with a bottom border exports as an empty line, not `---`; the fallback | probe 13 |
| Set a list's start number | none in place; the fallback | probe 10 |
| Nest an item of an existing list | re-create the list (the fix-up above); the glyph reset it causes, `-` to `*`, could be absorbed by a normalizer rule mapping `*` and `+` to `-`, not built, since fixture 12 shows markers kept today | probe 9b |
| Trust the Drive `version` after a `batchUpdate` | the script's guard already compares the normalized export, which showed every edit at once in every probe that read one; only the number lags; a Docs path guards on `requiredRevisionId` | probe 7, probe 6b step o |
| Map export lines to paragraphs by position | look a paragraph up by text it contains, as [h.py](PT-009/h.py)'s `find` does, which stops when the text is not unique; a sync would fall back to the replace there | every probe |
| Keep a comment on text the push replaces | edit inside the paragraph, word by word, so anchors on the unchanged words stay; a moved paragraph is a delete and an insert and loses its anchor; the carry-over above re-anchors by text | probe 5 (Alpha), probe 14b |
| Keep `pull` from reading a pending suggestion as accepted text | the paragraph text of `documents.get` with `suggestionsViewMode: PREVIEW_WITHOUT_SUGGESTIONS` differed from `SUGGESTIONS_INLINE` for an inserted suggestion, so `pull` could warn or stop; a suggested deletion or style change would leave that text alike, untested; the markdown export has no such switch | probe 13 |

## What a build would take

A hybrid, PD-001's C': diff the normalized lines, map each hunk to paragraphs by text, and send the requests above
for headings, prose paragraphs, blank lines and flat list items; fall back to the whole replace when a hunk
touches a checkbox state, list nesting, a table, a code block, an image or a rule, or when the mapping is not one
to one. Guard the Docs path with `revisionId` and keep the Drive `version` for the replace. Every fix-up in the
second table is a rule the mapping must know. Expect days, as PD-001 says, and a second write path to test against
the merge. For a task list the fallback runs on most syncs, since a tick is the common edit; for prose with
comments the edits keep every comment that is not on changed text.
