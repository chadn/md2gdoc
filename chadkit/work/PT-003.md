# PT-003 - OAuth desktop client, proven on both APIs

The client in `client_secret.json` (Cloud project `md2gdoc-2026`, Desktop app, consent screen External, in
Testing status on the day) works under the one scope `drive.file` on the Drive API and the Docs API. Proof: one
run of [PT-003/probe.py](PT-003/probe.py) on 2026-10-22, consent once in the browser, then on one scratch Doc,
trashed at the end:

| Call | Result |
| --- | --- |
| `InstalledAppFlow.run_local_server`, scope `drive.file` | `token.json` written with a refresh token |
| Drive `files.create`, markdown body to a native Doc | id `1ZMRTRqWHbhKT8IND-ik71JJxUco58KC0o9n3lXY__Xg`, version 4 |
| Docs `documents.get` | title and body returned |
| Docs `documents.batchUpdate`, one `insertText` at index 1 | accepted; the text took the title's heading style |
| Drive `files.export`, `text/markdown` | the inserted line came back first |
| Drive `files.update`, markdown body | same id and link, version 4 to 7, new content exported |

What this settles beyond PT-003: item 1 of "What is not proven" in [docs/design.md](../../docs/design.md), in-place
update keeps the link; and two observations for later tasks: the Drive `version` moved by three on one update, so
the push guard compares content, not steps (PT-007), and text inserted by `batchUpdate` inherits the previous
paragraph's style, so PT-009 must set paragraph style explicitly.

Run the probe again from the repository root with `uv run --script` on that file and `.` as its argument; it
reuses `token.json` when present. The consent screens seen are described in [docs/setup.md](../../docs/setup.md).
